# Е-Шлюз · PWA-демо

Демонстрация обмена документами между реальными людьми через интернет. React + TypeScript + Vite, Supabase Auth / Postgres / Storage / Realtime, Mail.ru SMTP (или Resend). Без интеграции с 1С.

## Что сделано

- Вход по ссылке из письма; доступ любому, кто подтвердил свой email.
- PDF, DOCX и XML до 10 МБ; от 1 до 10 адресатов в одной отправке.
- Индивидуальные состояния каждого получателя: ожидает подписи, подписан, отказ, карантин.
- Ответное демо-подписание и мотивированный отказ.
- Маршрут Direct B2B для договоров и актов, симуляция СБИС для УПД.
- Четыре уровня контроля с явным обозначением имитации; реальные SHA-256, ограничение файла и ID операции.
- Повторная проверка карантина, журнал событий, автоматическое обновление и Realtime.
- Реальное скачивание оригинала с проверкой SHA-256; ZIP с оригиналом, manifest.json, квитанциями, HTML-протоколом для печати в PDF и макетами .sig.
- Локальное демо с двумя переключаемыми участниками; хранение в IndexedDB. Этот режим не отправляет письма и не обменивается файлами между разными устройствами.
- PWA-манифест, иконки, установка. Для работы нужен интернет; приватные файлы и API не кэшируются service worker.
- CI, GitHub Pages и workflow GitHub Release по тегу v*.

**Граница демо:** ГОСТ, КЭП, PKI, OCSP, TSP, глубокая проверка содержимого, семантическая сверка и внешние операторы имитируются. Проверка расширения не является антивирусной проверкой. `.sig` — JSON-макеты, не CMS/CAdES. Архив не является юридическим доказательством или готовым пакетом для суда/ФНС. Тариф 15 ₽ — условная модель, не действующий тариф провайдера.

## Быстрый локальный запуск

Нужен Node.js 22.12+ (или актуальный Node.js 24).

```sh
npm install
npm run dev
```

Откройте адрес, который напечатает Vite. Кнопка «Открыть локальное демо» не требует настройки. В журнале отправленных есть образец документа. Откройте карточку, скачайте архив, переключите участника в верхней полосе и подпишите документ в ответ. Демо-PIN — `12345678`.

Локальное демо отделено от онлайн-данных: введённые в нём адреса не получают письма. Реальные документы используйте только после подключения Supabase и почты.

## Онлайн-обмен: настройка один раз

### 1. Supabase

1. Создайте новый проект на https://supabase.com .
2. В SQL Editor последовательно выполните `supabase/migrations/202611130001_initial.sql` и `supabase/migrations/202611130002_smtp_delivery.sql`. Старая схема из исходных материалов несовместима с этой версией; используйте новый проект, чтобы избежать конфликтов.
3. Получите Project URL и публичный anon/publishable key в настройках API.
4. Скопируйте `.env.example` в `.env`, заполните `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. В клиенте допустим только публичный ключ — **никогда не service_role**.
5. В Authentication включите Email и разрешите регистрацию новых пользователей. Пароль не нужен.
6. В URL Configuration задайте Site URL: точный адрес опубликованной PWA, например `https://foxyevilmp.github.io/DemoE/`. В Redirect URLs добавьте `https://foxyevilmp.github.io/DemoE/**` и для локальной разработки `http://localhost:5173/**`, `http://127.0.0.1:5173/**`. Это сохраняет ссылку на документ при входе.
7. Шаблон Magic Link должен содержать `{{ .ConfirmationURL }}`. При переходе по письму пользователь вернётся в PWA с сессией Supabase.

Без собственных настроек SMTP встроенная отправка Supabase ограничена и не подходит для входа любого адресата. Настройте SMTP до теста с двумя людьми.

### 2. Почта: Mail.ru SMTP

Домен не требуется: для небольшого демо письма могут уходить с существующего ящика Mail.ru. Получатель может пользоваться любой почтой. Адрес входа в PWA и настроенный сервер отправки — разные параметры.

1. В Mail.ru откройте Настройки → Все настройки → Безопасность → Пароли для внешних приложений и создайте отдельный пароль для Е-Шлюза с доступом к SMTP. Основной пароль от почты не используйте. При необходимости разрешите доступ по SMTP в разделе внешних сервисов.
2. В Supabase → Authentication → SMTP Settings включите собственный SMTP:

| Настройка | Значение |
| --- | --- |
| Host | `smtp.mail.ru` |
| Port | `465` |
| Шифрование | SSL/TLS |
| Username | Полный адрес вашего ящика Mail.ru |
| Password | Пароль для внешнего приложения |
| Sender email | Тот же адрес Mail.ru |
| Sender name | Е-Шлюз |

Это подключение отправляет ссылки для входа. Проверьте лимиты Supabase Auth и Mail.ru в настройках сервисов.

3. Для уведомлений о документах задайте отдельно в Supabase → Edge Functions → Secrets:

```dotenv
MAIL_PROVIDER=smtp
SMTP_HOSTNAME=smtp.mail.ru
SMTP_PORT=465
SMTP_USERNAME=YOUR_ADDRESS@mail.ru
SMTP_PASSWORD=YOUR_APP_PASSWORD
MAIL_FROM=YOUR_ADDRESS@mail.ru
APP_URL=https://foxyevilmp.github.io/DemoE/
```

Никогда не вводите SMTP_PASSWORD в PWA, не отправляйте его в чат и не сохраняйте в GitHub. При использовании CLI создайте игнорируемый файл `server.env.local` и выполните:

```sh
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase secrets set --env-file server.env.local
npx supabase functions deploy notify-document
```

Функция отправляет отдельное письмо каждому адресату. From — настроенный ящик Mail.ru; Reply-To — подтверждённый email отправителя документа. Принимающие серверы могут задерживать письма или относить их в спам. Статус «принято почтовым сервисом» не является подтверждением доставки в ящик.

SMTP не поддерживает ключи идемпотентности. Если результат отправки неизвестен (например, соединение оборвалось после передачи письма), функция не повторяет его автоматически. В карточке появится неопределённый статус; администратор проверяет отправку и только затем может сбросить задание в БД. Документ при этом остаётся доступен в PWA. Для принятых писем повтор не выполняется. После явно неуспешной попытки повтор разрешён с интервалом две минуты; общий срок повтора — 23 часа.

Поддержан и альтернативный Resend: `MAIL_PROVIDER=resend`, `RESEND_API_KEY`, `MAIL_FROM` на подтверждённом домене. SMTP и Resend одновременно не используются. Для массовой рассылки нужен подходящий транзакционный сервис; личный ящик здесь используется как транспорт небольшого демо.

Официальные инструкции: [Mail.ru](https://help.mail.ru/mail/login/mailer/), [SMTP Supabase](https://supabase.com/docs/guides/auth/auth-smtp), [пример SMTP Edge Function](https://github.com/supabase/supabase/tree/master/examples/edge-functions/supabase/functions/send-email-smtp).

### 3. GitHub Pages

1. Создайте репозиторий, `DemoE`, и загрузите проект без `.env` и `node_modules`.
2. В Settings → Pages → Source выберите **GitHub Actions**.
3. В Settings → Secrets and variables → Actions → **Variables** задайте:

| Переменная | Значение |
| --- | --- |
| `VITE_SUPABASE_URL` | Project URL |
| `VITE_SUPABASE_ANON_KEY` | Публичный anon/publishable key |
| `VITE_BASE_PATH` | `/DemoE/` или `/` для собственного домена |

4. После push в `main` workflow `Publish PWA` выполнит тесты, сборку и публикацию.
5. Укажите итоговый URL также в Supabase Auth и в секрете `APP_URL` функции.

Если публичные настройки Supabase не заданы, сборка откроется только с локальным демо — онлайн-вход будет явно недоступен.

### 4. Релиз на GitHub

После первого успешного деплоя:

```sh
git tag v0.1.0
git push origin v0.1.0
```

Workflow `Release` прогонит тесты, соберёт приложение и создаст GitHub Release с `e-shlyuz-pwa.zip`. Исходники GitHub приложит к тегу автоматически. Публикация сайта и GitHub Release — отдельные workflows. Для изменения исходников делайте новый тег; существующий опубликованный тег не перезаписывайте.

## Проверка в два устройства

1. Участник A открывает PWA, вводит свой email, переходит по письму.
2. A выбирает документ, вводит email B (или B и C), подписывает демо-PIN и отправляет.
3. Проверьте статус почтового уведомления в карточке. Если отправка не удалась, файл уже сохранён; не создавайте дубликат, повторите только уведомление.
4. B переходит по ссылке из письма, входит под email B. Скачивает/просматривает оригинал и проверяет SHA-256.
5. B подписывает или отказывает с причиной. A видит изменение; C принимает решение независимо.
6. Отправьте отдельный документ со сценарием карантина. У B он появится в карантине; после повторной демо-проверки доступна подпись.
7. Отправьте УПД: карточка показывает симуляцию коннектора СБИС.
8. Скачайте ZIP: в нём должны быть исходные байты файла и соответствующий SHA-256 в конверте.
9. Пользователь D, которому документ не адресован, не должен видеть его в списке или скачивать по пути Storage. Проверяйте это с отдельной сессией, не локальными пресетами.

## Контроль доступа и ограничения

- RLS на всех таблицах, закрытый Storage bucket; клиентам разрешено только чтение доступных записей.
- Изменения проходят через RPC: email берётся из подтверждённой сессии; отправитель не может подписать за получателя.
- Решения получателей терминальны; повторные запросы не порождают вторую подпись. В SQL запись решения и квитанция атомарны.
- Идемпотентность ID операции не запрещает человеку намеренно отправить тот же файл второй раз новой операцией.
- Участникам одного документа видны остальные его адресаты, их решения и история.
- В демо есть лимит 20 отправок в час на пользователя и 10 получателей. Перед открытым массовым использованием дополнительно настройте CAPTCHA, лимиты Supabase Auth и лимиты почтового транспорта.
- Нет антивируса, OCR, реального ГОСТ, 1С, финансовых проводок, сертификатов государственных УЦ, реального P2P/mTLS или интеграции с СБИС.
- Маршрут Direct B2B показан как продуктовая модель; реальные байты передаются через Supabase, а не напрямую между браузерами.
- Синхронизация: Realtime плюс резервный опрос каждые 15 секунд.
- Первичная структура SQL предназначена для нового проекта. Миграции уже запущенного приложения добавляйте отдельными файлами, не заменяйте историю.

## Команды

```sh
npm test
npm run build
npm run preview
```

Автотесты проверяют адресатов, состояния нескольких получателей, SHA-256, безопасную печатную форму и содержимое ZIP. Интеграционная проверка Supabase, RLS и доставки писем требует подключённого проекта и настоящих аккаунтов; клиентские тесты её не заменяют.
